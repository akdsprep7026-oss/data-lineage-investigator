## What happened along the way

1. **Added `etl_agent_node` and `schema_agent_node`** (`app/graph/etl_check.py`,
   `app/graph/schema_check.py`), wired into the graph between `data_quality`
   and `root_cause`.
2. **`manager_node` now scores keywords in the issue description**
   (`_select_agents_for_issue` in `app/graph/nodes.py`) instead of always
   running every specialist -- e.g. "missing"/"lower than expected" schedules
   `sql_analysis` + `data_quality`; "failing"/"no data" schedules `etl_agent`;
   "database error"/"column" schedules `schema_agent`. Falls back to running
   everything if no keywords match. `RETRY_PLAN`'s pipeline- and schema-related
   gaps now retarget `etl_agent`/`schema_agent` instead of `data_quality`/
   `sql_analysis`, since those two now do that job more directly.
3. **Found and fixed a real bug while dogfooding the new agents**:
   `validation.py`'s `classify_claim` didn't recognize "column is missing
   from..." as a schema-change claim (only "missing column", "renamed", etc.),
   so a substantively-correct incident #3 hypothesis kept getting
   reclassified as `unclassifiable_claim` and looped to the retry cap instead
   of being confirmed. Fixed by broadening the schema_change keyword list
   with phrasings that don't collide with the other claim kinds.
4. **Found and fixed a real evidence-quality gap for incident #4**: the
   original `data_quality_node` only counted duplicates of the *same*
   `order_id` -- which incident #4 doesn't have any of (each re-emitted order
   gets a brand-new id) -- so the LLM had to infer the "different id, same
   transaction" mechanism purely from prose SQL review, with mixed results.
   Added a `duplicate_transaction_groups` check to `app/graph/data_quality.py`
   (rows sharing `customer_id`/`amount`/day under more than one distinct id),
   mirroring the check `validation.py`'s independent re-check already used.
   This measurably improved incident #4 across repeated runs (previously as
   low as an unresolved, wrong-file guess; now a resolved, mostly-correct
   answer) -- exactly the "improve evidence quality, don't add more agents"
   guidance for a below-bar result.

## Known gap (carried into the Gemini run)

Incident #4's dedup evidence (`duplicate_transaction_groups`) surfaces the
*fact* that customer/amount/day groups have more than one id, but not *which*
ids are old vs. new -- so the LLM sometimes reasons about the right general
shape (order_id-based dedup is insufficient) but the wrong specific mechanism
(same id / newer timestamp, instead of different id / same transaction). If
the Gemini run also lands on this same partial pattern for #4, the next
targeted improvement would be enriching that evidence string with the actual
duplicate id values so the LLM has less room to guess, rather than adding
another agent.
